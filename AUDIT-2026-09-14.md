# Website audit — 14 September 2026

Scope: local source, full dependency audit, lint, existing successful production build, local browser checks, image delivery, and public HTTPS response headers. No emails were sent, no load attack was performed, and application code was not changed during this audit. Local uncommitted changes mean findings are not all verified against the deployed revision.

## Priority findings

1. **High: enquiry abuse protection is missing in application code.** `src/app/api/enquiries/route.ts` accepts public requests without rate limiting, bot verification or duplicate suppression. An attacker could fill the business inbox and consume the email allowance. The recipient is fixed, so this is not an arbitrary-recipient mail relay. Vercel account-specific firewall rules were not inspected. Add a persistent rate limit and bot protection before calling Resend.
2. **High if still active: previously shared Resend credential.** A key was pasted into the conversation earlier. Rotation status is unknown. Replace it in local and Vercel settings and revoke the old key; never put it in client code. No matching key was found in the scanned non-environment working files, and no environment files were listed as tracked by Git. This was not a full Git-history or account audit.
3. **Medium: server validation is incomplete.** The endpoint only verifies required values are nonempty strings. It does not validate email/phone format, enforce field/body size limits, or look up a trusted catalog design. A caller can invent codes, categories and image paths. Truthy non-string optional values cause exceptions. Add a strict schema and server-owned design lookup. HTML field escaping is already present, which is good.
4. **Medium: consultation form permits incomplete submissions.** `src/components/Consultation.tsx:94` omits required attributes, while the endpoint requires name, email and phone. Blank submissions reach the channel picker and then fail by email. Validate before opening the picker and explain field errors.
5. **Medium: catalog phone validation is broken.** At `src/app/catalog/Catalog.tsx:124`, the pattern is incompatible with modern HTML pattern syntax. A browser check using `abcdefgh` returned `valid: true` and `patternMismatch: false`. Fix the pattern and validate server-side too.
6. **Medium: duplicate requests and stale status.** Catalog form changes reset sending status to idle, re-enabling submit during a pending request. Closing/reopening can let an old response update the new enquiry. Consultation also retains status between attempts. Lock a submission snapshot, guard concurrent sends and ignore stale responses; add server-side idempotency.
7. **Medium: production email setup still uses the testing sender.** The endpoint hardcodes `onboarding@resend.dev`. Resend limits this sender to the account owner's email. Verify the business domain in Resend and use a sender on it for production. No successful delivery was tested in this audit.
8. **Hardening: response headers.** The live homepage includes HSTS, but the inspected response lacks Content-Security-Policy, frame protection, X-Content-Type-Options and an explicit Referrer-Policy. Add tested headers; absence alone does not establish a compromise. No application database, login or payment flow was found in the reviewed scope.

## Other functional issues

- Consultation channel dialog lacks focus trapping and Escape handling despite `aria-modal=true`.
- Catalog text incorrectly promises an email review step before sending; the backend sends directly.
- No explicit timeout or structured error logging around the email provider call. A provider failure gives little diagnostic information; do not log customer message bodies or secrets when improving logging.
- Full lint: **3 errors, 2 warnings**. State changes inside effects are flagged in CustomCursor, IntroTransition and Navbar. Hero has two unused values. These are code-quality issues, not proof of runtime crashes or a breach.

## Performance and pictures

- Next.js production build passed immediately before this audit. Routes are statically generated except the enquiry API.
- All five local public pages, sitemap and robots returned HTTP 200 in the preceding verification.
- Catalog browser rendered 30 designs; the enquiry dialog opened successfully. At the inspected 702 px viewport there was no horizontal page overflow. This is not a complete device matrix.
- Catalog uses responsive Next Image output, lazy loading and reserved aspect-ratio space.
- Measured local image: `gce47.png` original **2,623,640 bytes**, optimised at width 750/quality 75 with WebP acceptance **40,632 bytes** (about 98.5% smaller). This is one sample, not all production images.
- 31 source images total **69,614,779 bytes**. Browsers do not download all originals at initial load, but email images use original URLs, and source sizes still affect storage and cold optimisation. Consider smaller web-ready originals after visual comparison.
- Several homepage fill images omit explicit sizes. Full-width hero defaults are reasonable; smaller gallery/craftsmanship areas can request unnecessarily large images. Supply accurate sizes per layout.
- Intro overlay and reveal animations add perceived waiting, and the homepage has continuous motion. Measure on a throttled mobile device before declaring loading speed good.
- Public apex and www HTTPS requests completed with HTTP 200 after redirects, HSTS, and Vercel cache HIT. Observed end-to-end request times were about 9.9s and 15.2s from this tool environment, including connection/redirect overhead. These are **not browser load times or Core Web Vitals** and cannot establish real-user performance. Initial sandbox network failures were environmental, not evidence of an outage.
- No reliable production Lighthouse score, LCP, INP or CLS measurement was obtained. Production performance remains unverified; run mobile PageSpeed Insights after deployment and examine real-user data when available.

## Passed checks and limits

- `npm audit --json` and production-only audit reported **0 known vulnerabilities**. This does not prove that the application is secure.
- HTML email values are escaped and the API credential is read on the server.
- No common credential patterns were found outside ignored environment/build/dependency folders in the working-tree scan. A complete historical secret scan was not performed.
- Account MFA, permissions, DNS ownership, Vercel firewall settings and Resend account security were not audited.

Recommended order: rotate the shared key if necessary; protect and validate the enquiry endpoint; fix form validation/submission state; configure the verified sender and browser security headers; then optimise and measure mobile performance.
